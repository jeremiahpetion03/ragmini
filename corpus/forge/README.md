# Forge

A harness for **creating, solving, and grading ML engineering tasks**, built on one premise: *a grader is only trustworthy if it is proven to catch wrong answers.*

Each task ships with a spec, starter code, a reference solution, hidden checks, and a set of **planted mutants**: realistic wrong solutions of the kind people actually write. Forge certifies a task only if:

1. the **reference passes** every check,
2. results are **identical across repeated runs** (no flaky grading),
3. the **starter code fails**, so the task is not already solved, and
4. **every mutant fails** at least one check, so the grader doesn't accept wrong answers.

```bash
pip install numpy pytest
python -m forge list                                   # show tasks
python -m forge grade 04_kv_cache_attention my_sol.py  # grade a solution
python -m forge validate --runs 10                     # certify every task, write VALIDATION.md
python -m forge check-report                           # fail if VALIDATION.md is stale
pytest                                                 # harness tests
```

## The tasks

| Task | What it tests | Example mutant it catches |
|---|---|---|
| **Numerically stable log-softmax** | overflow and underflow, masking with −inf, dtype preservation, `axis` handling | subtracts the mean instead of the max, so it still overflows in float32 |
| **LayerNorm backward pass** | gradients vs finite differences, low-variance rows, shift-invariance (Σdx = 0) | correct gradients, but scales `dy` in place, corrupting the caller's tensor |
| **Gradient accumulation** | exact equivalence to full-batch gradient with uneven and empty micro-batches | numerically perfect, but concatenates every micro-batch, defeating the memory limit |
| **KV-cache attention** | matches full causal attention, stability, instance isolation, ≥3x speedup | cache stored on the class, so two generations at once corrupt each other |
| **Leak-free train/val split** | no user in both splits, row-fraction accuracy, seed reproducibility, randomness | leak-free and the right size, but always picks the lowest user ids |
| **Distances under a memory budget** | peak memory < 3x output (tracemalloc), no negatives, accuracy far from the origin | memory-efficient but uncentered: catastrophic cancellation gives 2.4e-4 error |
| **nDCG@k for ranking evaluation** | graded relevance, tie-breaking, queries with no relevant documents, k > N, ≥5x faster than a per-query loop | builds the ideal ranking from only the retrieved documents, inflating every score |
| **Leak-free feature preprocessing** | train-only statistics, a row alone = the same row in a batch, NaN-aware stats, unseen categories, constant columns | recomputes statistics from each transform batch: leakage and train/serve skew |
| **Tiled attention with online softmax** | the FlashAttention algorithm: running max and sum per query, any tile size, masked tiles, memory < 50% of the score matrix | never skips a fully masked tile, so `-inf - (-inf)` gives NaN |
| **Locate the first non-finite value** | stop at the first layer emitting NaN, +inf or -inf; snapshot its input before in-place layers mutate it; counts and first position | checks only for NaN, so it blames the later layer where `inf - inf` became NaN instead of the layer that overflowed |

Each task's `README.md` is the spec a solver sees. `grader.py` holds the hidden checks.

## How the checks were made trustworthy

**Each check tests one property.** Early versions of two graders mixed properties: the memory check also re-verified correctness, and the isolation check compared against the correct answer. That made wrong-but-independent solutions fail the isolation check for the wrong reason. Both now test exactly one thing. The isolation check, for example, compares a cache used alongside another against *the same solution run alone*. The mutant tables in [VALIDATION.md](VALIDATION.md) show which check caught each bug.

**Every threshold has a measured margin on both sides:**

| Check | Correct solution | Threshold | Planted mutant |
|---|---|---|---|
| KV-cache speedup vs re-projecting history | 14.2x | ≥ 3x | 2.0x (rebuilds cache array each step) |
| Peak memory / output size | 1.09x | ≤ 3x | 4.08x (out-of-place temporaries); 65x (starter) |
| Self-distance error, points near 1e5 | 2e-14 | < 1e-8 | 2.4e-4 (no centering) |
| nDCG@k speedup vs per-query loop | 14x | ≥ 5x | 0.6x (starter) |
| Tiled attention peak memory / full score matrix | 15% | ≤ 50% | 106% (writes scores into a full buffer); 300% (starter) |

The speed checks compare against a baseline timed **in the same process** (best of 3), so they hold on slow and fast machines alike.

**The validator is itself tested.** `tests/test_harness.py` builds deliberately broken tasks and requires Forge to reject them: a task whose reference fails, a task whose grader can't distinguish an *equivalent mutant* (`x + x` vs `2 * x`), and a task with a coin-flip check that must be flagged as flaky.

**Submissions are isolated.** Each solution runs in a fresh interpreter (`python -I`) in a scratch directory with a time limit. Tests confirm that infinite loops time out, syntax errors and hard crashes (`os._exit`) are reported rather than raised, solution output can't corrupt result parsing, and no state carries between runs. *This is process isolation, not a security sandbox: run untrusted code inside a container or VM.*

**Reports can't go stale.** `validation.json` records the Python, NumPy and platform it was produced on, the git commit, and a SHA-256 of every file that defines each task (CRLF normalized to LF, so Windows checkouts hash the same). `python -m forge check-report`, run in CI and as a test, fails if any task was edited, added or removed since the report was generated.

## Adding a task

```
tasks/11_your_task/
  task.json      title, difficulty, skills, time_limit_s
  README.md      the spec solvers see
  starter.py     code handed to solvers (must fail)
  reference.py   a correct solution (must pass)
  grader.py      hidden checks, written with @check(name, weight, kind)
  mutants/*.py   realistic wrong solutions (each must fail)
```

Then run `python -m forge validate 11_your_task`. It tells you exactly which condition fails.

## CI

Every push checks that the committed report is current, runs the harness tests, and certifies every task 10 times, on Ubuntu (Python 3.11, 3.12) and Windows (Python 3.12).
